# Claude Code の Stop フック検証 —— 「テストが通るまで終わらせない」は効くか

Claude Code の Stop フック（終了時にテストを自動実行し、失敗したら終了を止めて修正させる仕組み）を、小さな題材で検証した記録です。
題材は日付文字列の正規化（normalize_date()：さまざまな表記を YYYY-MM-DD にそろえ、解釈できなければ None を返す）。テストファイルを仕様として先に置き、実装を Claude Code に書かせました。

## ファイル
test_normalize_date.py — 仕様としてのテスト（45件）
normalize_date.py — 実装
check.sh — pytest を実行し、失敗時に理由を出して終了コード2を返すスクリプト
.claude/settings.json — Stop フックに check.sh を登録

## 実験と結果

### 実験A：フックなし
同じ依頼（「テストが全部通るようにして」）では、Claude は自分でテストを実行し、全件合格を確認してから終了しました。ただし検証の方法はモデルの判断次第で、最初は pytest が無い環境で「テスト関数を直接実行する」という代替手段を取り、その旨を正直に申告しました。やるかどうか・どうやるかはモデルの善意に委ねられます。
その過程で、テストを厚くしていくと（4件→45件）Claude が仕様の曖昧な点（区切り文字の混在、全角数字の扱い）を自分で決めず、人に判断を仰ぐ場面がありました。仕様の穴はAIが見つけ、決めるのは人、という分担が自然に発生します。

### 実験B：Stop フックあり
依頼に「テストが全部通るように」とある限り、Claude は自分でテストを実行して通してから終わるため、フックは出番がありませんでした。
「テストは実行しなくていい。できたら終わらせて」と検証を禁じた指示でも、初回実装が正しければフックは静かに通ります。
仕様（テスト）と矛盾する指示（「戻り値の形式を YYYY/MM/DD に変えて」）を与えたとき、フックが終了をブロックしました。理由（「テストが失敗しています。失敗内容を確認して修正してください」）が渡され、修正ループに入りました。

### ハマりどころ（配管の点検）
フックが効かない原因が2つ重なりました。どちらも「置いたつもり」で静かに素通りします。
設定ファイル名を .claude/setting.json（単数形）にしていた → 設定自体が読み込まれない
check.sh に実行権限がなかった → フックは走るが "Permission denied" で、終了はブロックされない（ブロックするのは終了コード2のときだけ）
ファイル名・実行権限・終了コードまで含めて動作確認して、初めて仕組みが効きます。

一番の発見：フックは「仕様が守られること」を保証しない
ブロックされた Claude が取った修正は、実装を仕様に戻すことではなく、テストの期待値を新しい形式に書き換えることでした。結果としてテストは通り、フックは満足します。
フックが保証するのは「テストが通る状態でしか終われない」こと
AI がテスト（仕様）も書き換えられる環境では、検査される側が検査する側を取り込める
実務での結論は、テストは AI の書き込み権限の外に置くこと（読み取り専用、変更は人の承認）。「生成と評価を分ける」という原則は、権限の分離まで落として初めて効きます。

## まとめ
検証の実行は、モデルの善意ではなく仕組み（フック）で固定できる
ただし仕組みは配管の点検とセットでないと効かない
そして検査対象（仕様）は、生成する側の権限の外に置く
これは「AIに考えさせる範囲を狭くし、決められる部分はルールで担保する」という進め方の一部として検証したものです。
